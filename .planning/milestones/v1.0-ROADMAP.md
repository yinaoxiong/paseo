# Roadmap: Paseo Native Cursor SDK Provider

## Overview

This milestone introduces Cursor SDK support as an experimental direct provider. The work starts with a low-risk SDK spike, then builds the provider lifecycle and event mapper, then connects built-in provider metadata and app UI, and finishes with focused tests and documentation. The existing Cursor ACP integration stays untouched throughout the milestone.

## Phase Details

### Phase 1: SDK Viability Spike

**Goal**: Produce an evidence-backed spike proving whether `@cursor/sdk` can support the required local provider lifecycle inside Paseo.
**Depends on**: Nothing (first phase)
**Requirements**: [SDK-01, SDK-02, SDK-03]
**Success Criteria** (what must be TRUE):

1. The SDK can be imported from the server workspace without destabilizing existing workspace builds.
2. A minimal local SDK agent can create, send, stream, wait, cancel, and resume in a Paseo-compatible runtime.
3. Auth, config, startup, and in-run failure modes are documented for provider implementation.
4. The spike concludes with a recommendation to proceed, adjust scope, or stop.
   **Plans**: 2 plans
   Plans:
   **Wave 1**

- [x] 01-01: Run and document SDK local lifecycle experiments.

**Wave 2** _(blocked on Wave 1 completion)_

- [x] 01-02: Design provider state, persistence handle, error mapping, and mode mapping from spike findings.

### Phase 2: Direct Provider Core

**Goal**: Add the experimental `cursor-sdk` direct provider with local session lifecycle, persistence, cancellation, and Sandbox/YOLO mode handling.
**Depends on**: Phase 1
**Requirements**: [PROV-01, PROV-02, PROV-03, PROV-04, PROV-05, MODE-01, MODE-02]
**Success Criteria** (what must be TRUE):

1. Paseo can create a local Cursor SDK session through a direct provider class.
2. Submitted user prompts create canonical Paseo user timeline rows.
3. SDK stream output becomes Paseo assistant, tool, reasoning, usage, and completion events where available.
4. The persistence handle is sufficient to resume a Cursor SDK session after daemon restart.
5. Sandbox and YOLO map to explicit SDK runtime options and YOLO is marked unattended.
   **Plans**: 3 plans
   Plans:
   **Wave 1**

- [x] 02-01-PLAN.md — Add provider dependency boundary, client class, registry factory, and availability checks.

**Wave 2** _(blocked on Wave 1 completion)_

- [x] 02-02-PLAN.md — Implement session lifecycle, local store path, resume handle, and cancellation.

**Wave 3** _(blocked on Wave 2 completion)_

- [x] 02-03-PLAN.md — Implement stream event mapping and canonical timeline behavior.

### Phase 3: Manifest and UI Integration

**Goal**: Surface the experimental provider in Paseo's built-in provider metadata, app controls, mode visuals, and model/thinking option surfaces.
**Depends on**: Phase 2
**Requirements**: [MODE-03, FEAT-01, FEAT-02, FEAT-03, UI-01, UI-02, UI-03]
**Success Criteria** (what must be TRUE):

1. The provider is visible as an experimental built-in provider with clear copy.
2. The app renders Cursor SDK provider icon/name/modes through existing provider selection and composer controls.
3. Sandbox and YOLO are the only v1 modes shown to users.
4. Model and thinking controls use SDK metadata only where stable and avoid scratch sessions for discovery.
5. Existing Cursor ACP catalog/provider behavior is unchanged.
   **Plans**: 4 plans
   Plans:
   **Wave 1**

- [x] 03-01: Add provider manifest metadata, mode visuals, and icon wiring.

**Wave 2** _(blocked on Wave 1 completion)_

**Wave 3** _(blocked on Wave 2 completion)_

- [x] 03-03: Verify provider/model/thinking selection behavior for the side-by-side Cursor providers.

**Wave 4** _(blocked on Wave 3 completion)_

- [x] 03-04: Wire fast feature preference pruning and composer feature integration.

### Phase 4: Hardening, Tests, and Docs

**Goal**: Prove the integration with targeted tests, document user-facing behavior and limitations, and run required verification commands.
**Depends on**: Phase 3
**Requirements**: [MODE-04, UI-03, QUAL-01, QUAL-02, QUAL-03]
**Success Criteria** (what must be TRUE):

1. Targeted tests cover provider registration, mode metadata, event mapping, persistence, and resume behavior.
2. Documentation explains SDK auth, local runtime, Sandbox vs YOLO, and omitted Ask/Agent modes.
3. Typecheck and lint pass after implementation changes.
4. The final summary calls out remaining SDK beta risks and follow-up v2 opportunities.
